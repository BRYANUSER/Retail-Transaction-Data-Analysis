### 關鍵發現：CUSTCD / ITEMID 讀取型態問題

原始讀取程式未指定欄位型態，pandas 會自動把 `CUSTCD`、`ITEMID` 推斷成數字，兩欄各自出問題：

**CUSTCD**（20 位數字，超過 int64 的精確表示範圍，會落到 float64）

- 前導 0 被吃掉 → 20 位變成 19 位
- 尾端精度誤差 → float64 只有約 16 位有效數字，第 17 位之後會被歸零，**不同的兩位顧客可能被壓成同一個 ID**

這兩者裡，第二種嚴重得多：前者只是 ID 變短，後者是直接汙染顧客歸屬，會讓 FQMA、購物籃這類「以人為單位」的分析整個失準。

**ITEMID**（因欄位存在缺失值，被自動轉成 float64，顯示成 `317395.0` 這種格式）

- 連帶讓診斷腳本裡的「非純數字」檢查全數誤判為異常

**處理方式**：讀取時明確指定 `dtype={'CUSTCD': str, 'ITEMID': str}`。

**驗證結果**：改成字串讀取後，兩欄的長度與格式都恢復正常。這證實了上表那 242 筆「長度異常」與 ITEMID 的浮點格式**都是讀取時造成的假象，資料本身並沒有壞**，因此除了「內容全為 0」的 222 筆之外，不需要再對 CUSTCD 做任何修補。

## 二、處理決策

| 項目 | 決策 | 理由 |
|---|---|---|
| CUSTCD / ITEMID 讀取型態 | ✅ 修正為字串型態讀取 | 避免前導 0 遺失與大數字精度誤差，影響後續顧客歸屬判斷 |
| CUSTCD 長度不一致（242 筆） | ⬜ 不處理 | **假警報**：改用字串讀取後長度即恢復正常，資料本身沒壞。其中內容全為 0 的 222 筆另依下一列處理 |
| ITEMID 誤判為浮點數 | ⬜ 不處理 | **假警報**：同上，字串讀取後格式正常，診斷腳本的「非純數字」檢查是被型態誤導 |
| ITEMID 缺失（799 筆） | ❌ 刪除 | 無法歸屬品項，資料無效 |
| CUSTCD 全為 0（222 筆） | ❌ 刪除 | 屬系統預設值，非真實顧客 |
| 交易日期為 1960（370,133 筆） | ❌ 刪除 | 系統預設值／缺失值，非真實交易日期 |
| UNITPOSPRICE 為 0 元（1,035,316 筆） | ✅ 保留 | 筆數比例不低（3.74%），研判可能為促銷組合／贈品項目未標價，非全為異常資料 |
| UNITPOSPRICE 負值（29,096 筆） | ❌ 刪除 | 視為異常，統一刪除，不特別區分退貨情境 |
| 完全重複列（2,849,549 筆） | ✅ 保留 | 無唯一交易編號，無法確定是否為真重複，避免誤刪真實交易 |

> **補充說明：「CUSTCD 讀取型態修正」與「刪除全 0 的 CUSTCD」是兩個不同步驟**
>
> - 讀取型態修正（改用字串讀取）套用在**全部** CUSTCD 資料上，確保內容不失真
> - 刪除全為 0 的 222 筆，是在資料**正確讀取之後**，針對「內容全部是 0」這種**特定值**做過濾，因為這代表系統的非會員／測試預設值，不是真實顧客
> - 兩者是先確保資料正確、再依內容意義做過濾，並不衝突

## 三、清洗流程與實際結果

清洗腳本依序執行：

1. 讀取原始資料並合併三年（`dtype={'CUSTCD': str, 'ITEMID': str}`、`encoding='utf_8_sig'`）
2. 解析日期欄位（`TRANSTIMESTAMP` → datetime，格式 `%d%b%Y:%H:%M:%S.%f`）
3. 刪除 ITEMID 缺失的資料
4. 刪除 CUSTCD 全為 0 的資料
5. 過濾交易日期為 1960 的資料
6. 刪除 UNITPOSPRICE 為負值的資料
7. 輸出至 `data/cleaned_transactions.csv`

`cleaned_transactions.csv` 為共用中繼檔，後續分析直接讀取、不重複清洗。

### 各年度筆數

| 年份 | 筆數 |
|---|---|
| 2014 | 9,704,506 |
| 2015 | 9,135,383 |
| 2016（1–10 月） | 8,461,504 |
| **合計** | **27,301,393** |

> **注意：這份年份分布是中間狀態，不是最終輸出筆數。**
> 三年加總 27,301,393＝原始 27,671,526 −370,133，剛好等於 1960 那批的筆數，一筆不差。也就是說這是「只扣掉 1960、其餘三項刪除尚未執行」時的統計。
> 最終檔案應再少掉 ITEMID 缺失 799 + CUSTCD 全 0 的 222 + 負值 29,096 ＝ **至多 30,117 筆**（三個條件可能互相重疊，所以是上限），估計最終約 **2,727 萬筆**。確切數字以腳本執行時印出的 log 為準，補上後再更新此處。

## 四、已知問題

### 2015 年 11 月整月缺失

下游的來店人數預測發現，可用資料實際上是 **2014-01~2015-10 + 2015-12~2016-10**，**2015 年 11 月整月沒有資料**。

各年筆數也支持這件事：

| 年份 | 筆數 | 月數 | 月均 |
|---|---|---|---|
| 2014 | 9,704,506 | 12 | 約 80.9 萬 |
| 2015 | 9,135,383 | 11（假設缺 11 月） | 約 83.0 萬 |
| 2016 | 8,461,504 | 10（1–10 月） | 約 84.6 萬 |

三年月均是平順的微幅成長。反過來，如果 2015 當成完整 12 個月來算，月均會掉到 76.1 萬，中間憑空凹一個洞，不合理。所以「2015 只有 11 個月」是站得住的解讀。

## 附錄、資料字典

### `cleaned_transactions.csv`

| 欄位 | 型別 | 意義 | 注意事項 |
|---|---|---|---|
| `CUSTCD` | str | 顧客卡號（會員與非會員皆有） | 20 位數字。**務必以字串讀取**，用數字讀會前導 0 遺失＋尾端精度誤差。全 0 者為非會員／系統預設值，已於清洗時刪除 |
| `TRANSTIMESTAMP` | datetime | 交易日期 | **只有日期精度，時分秒恆為 0；且沒有交易單號**，所以無法區分同一人同一天的不同次結帳 |
| `ITEMID` | str | 商品 ID | **務必以字串讀取**，否則會變成 `317395.0` 的浮點格式，字串比對與分群都會出錯 |
| `UNITPOSPRICE` | float | 購買價格 | 0 元約佔 3.74%（保留）；負值已刪除；**無數量欄位**，無法直接算件數 |

正確的讀取方式：

```python
df = pd.read_csv(
    'data/cleaned_transactions.csv',
    dtype={'CUSTCD': str, 'ITEMID': str},
    parse_dates=['TRANSTIMESTAMP'],
)
```
