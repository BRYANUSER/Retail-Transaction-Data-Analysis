## 1. 會員資料 join key 更正

> **使用程式**:`check_member_match.py` | **關鍵發現**:改用NBU_CARD重新比對後,78.7%的CUSTCD對得上會員資料;比較「對得上/對不上」兩群的Frequency分布(中位數3 vs 2次、平均9.7 vs 8.5次),發現對不上的顧客不是單次消費的雜訊ID,而是穩定可追蹤的非會員,據此判定應納入分析。

**問題**:原本用交易明細的 CUSTCD 去對會員資料的 `MEMBER_ID`(varchar(13)),完全對不上,一度懷疑是「非會員」。

**發現**:查看會員資料欄位說明後確認,正確對應欄位是 `NBU_CARD`(varchar(20),註明「客戶卡號,與交易明細的CUSTCD對應」),不是 `MEMBER_ID`。兩者長度、格式都不同,`MEMBER_ID`是會員系統內部編號,`NBU_CARD`才是卡號。

**改用NBU_CARD後的比對結果**:
- 交易明細中不重複的CUSTCD共 286,810 個
- 對得上會員資料(NBU_CARD):225,842 個(78.7%)
- 對不上:60,968 個(21.3%)

**對不上顧客的判讀**:比較「對得上」vs「對不上」兩群的Frequency(消費次數)分布,兩者非常接近(中位數3 vs 2次、平均9.7 vs 8.5次、單次消費比例31.7% vs 39.6%),不是「大多數只出現1次」的雜訊ID型態。同時抽樣檢查對不上的卡號,長度都是穩定的20碼(格式正常),但開頭幾碼跟常見會員卡號不同。

**決策**:對不上會員資料的顧客,判定為穩定可追蹤的「非會員」,**納入後續分析**,不排除。

## 2. 會員資料(member.csv/xlsx)欄位處理決策

> **使用程式**:`clean_member_data.py` | **說明**:下表的保留/捨棄決策由此腳本實作(`usecols`只挑需要欄位進記憶體、輸出`member_clean.csv`),決策理由本身來自資料欄位說明文件的檢視,不是程式跑出來的統計發現。

**原則**:原始檔案保留、不刪欄位;讀取時用 `usecols` 只挑需要的欄位進記憶體;另外產出一份清洗過的衍生檔案(`member_clean.csv`),避免每次分析都要重跑一次清洗邏輯。

| 欄位 | 決策 | 理由 |
|---|---|---|
| `NBU_CARD` | 保留,重點清洗 | join key,全程當字串處理,需檢查有無重複值(一卡對多筆會員紀錄會讓join膨脹) |
| `BIRTHDAY_Y` | 保留,計算年齡 | 年齡用「交易資料的年份」當基準,不是用現在的年份,避免年齡整體多算 |
| `BIRTHDAY_M` | 不用 |  |
| `SEX` | 保留,清洗異常代碼 | 只接受合理編碼(1/2),其餘轉缺失值 |
| `EDUCATION` | **捨棄** | 資料本身註明「資料不可信」 |
| `STORE_ID` | 保留 | 999是「集團其他來源」的特殊代碼,分析時當獨立類別處理,不當數值大小比較 |
| `BTIME` | 保留,計算入會年資 | YYYYMMDD字串格式,需過濾異常值(全空白/全零)再parse |
| `CTIME` | **捨棄** | 與顧客消費行為分群無直接關係,且缺值多 |
| `MEMBER_ID` | **捨棄**(此專案) | 內部系統編號,非join key,這次分析用不到;原始檔案仍保留該欄位 |
| `MUID` | **捨棄**(此專案) | 虛擬ID,無直接用途 |
| `E_DM` / `PROMOTION_MESG` / `SEND_DM` | **捨棄** | 行銷同意欄位,與消費行為分群無關,屬於行銷執行用途 |
| `ZIP_CODE5` | 保留 | 全程當字串處理,避免前導零被當數字讀取而遺失 |
| `ADD_STATUS` | **捨棄** | 地址正確性標記,這次分析用不到 |

## 2.0 member_clean.csv 輸出欄位定義

> **使用程式**:`clean_member_data.py` | **說明**:以下逐欄位定義是`clean_member_data.py`實際輸出邏輯的文字對照,供不需查閱程式碼時對照欄位定義使用。

清洗後輸出的每個欄位,精確定義如下(對照 `clean_member_data.py`):

- **NBU_CARD**:原始 `NBU_CARD` 去除頭尾空白與float轉換殘留的結尾 `.0`,當字串保留,做為join key。
- **Age**(年齡):`REFERENCE_DATE 的年份 - BIRTHDAY_Y`。注意基準是 `REFERENCE_DATE`(交易資料的時間範圍,例如2016年),不是今天的日期(2026年)。`BIRTHDAY_Y` 不在1900~REFERENCE_DATE年份之間視為異常,轉缺失值。
- **Sex**(性別):原始 `SEX` 清理後只接受 `"1"` 或 `"2"`,其餘(含空白、其他代碼)一律轉為缺失值,不做男/女轉換,保留原始編碼。
- **ZipCode5**(郵遞區號):原始 `ZIP_CODE5` 去除頭尾空白與 `.0` 殘留後,補齊左側0至5碼長度(避免前導零遺失)。
- **StoreId**(辦卡分店別):原始 `STORE_ID` 去除頭尾空白與 `.0` 殘留,原樣保留為字串類別,`999` 代表「集團其他來源」的特殊類別,不當數值大小比較。
- **TenureDays**(入會年資,天數):`(REFERENCE_DATE − BTIME) 的天數`。`BTIME` 是顧客第一次辦卡/加入會員的日期(原始格式YYYYMMDD字串),數字越大代表入會越久。`BTIME` 格式不是8位數字(例如全空白、殘缺)則整筆轉為缺失值。

## 2.1 清洗腳本bug修正紀錄

> **使用程式**:`clean_member_data.py`(第一版執行時發現的bug) | **關鍵發現**:`TenureDays`欄位100%缺失,追查後定位為`BTIME`欄位含結尾`.0`殘留導致8位數字格式檢查全部失敗;修正為統一用`clean_id_string()`處理`BTIME`/`SEX`/`STORE_ID`。

`clean_member_data.py` 第一版執行後,`TenureDays` 出現100%缺失的異常結果。排查後發現:`BTIME` 來源欄位被讀成帶小數點的字串(例如 `"20060622.0"`),清洗程式忘記套用跟 `NBU_CARD` 一樣「去除結尾.0」的處理,導致「8位數字格式檢查」全部判定失敗。已修正:`BTIME`、`SEX`、`STORE_ID` 統一改用 `clean_id_string()` 處理(去除頭尾空白與結尾的 `.0`),避免同類問題。

**教訓**:任何原始資料裡「看起來是數字」的欄位,只要曾經過Excel/資料庫的數字型態轉換,都有可能被加上多餘的 `.0`,清洗時要統一用同一套字串正規化函式處理,不要分別手刻。

**首次執行結果**(修正前,`TenureDays`需忽略,其餘為修正後仍有效的參考數字):

| 欄位 | 缺失比例 | 判讀 |
|---|---|---|
| NBU_CARD | 8.1% | 卡號本身缺失,推測是資料建檔時卡號欄位就是空的,屬於真實缺失,非格式問題 |
| Age | 0.1% | 生日年份異常或缺失的比例很低,資料品質良好 |
| Sex | 0.1% | 同上,資料品質良好 |
| ZipCode5 | 2.8% | 少部分會員沒有留郵遞區號 |
| StoreId | 0.0% | 全部有值 |
| TenureDays | 100%(bug) | 已定位為程式bug,修正後需重新執行確認實際缺失比例 |

## 2.2 第二輪修正:BTIME真實格式 + NBU_CARD重複值誤判

> **使用程式**:`clean_member_data.py`(第二輪修正,對照真實600萬筆`member.csv`實測) | **關鍵發現**:`BTIME`真實格式是`YYYY-MM-DD`(而非資料字典寫的`YYYYMMDD`);先前判定「NBU_CARD有49萬筆重複」是`.duplicated()`把多個NaN互相視為相等所致的誤判,排除缺失值後確認無重複。

在真正的 `member.csv`(600萬筆,而不是先前用來看欄位說明的Excel範例)上實測後,發現兩個問題:

**問題一:`TenureDays` 仍然100%缺失。** 加上診斷輸出後確認,`BTIME` 的實際格式是 `"YYYY-MM-DD"`(例如 `"2006-06-15"`,10個字元),跟一開始從「資料庫欄位說明」Excel看到的範例格式 `"20060622"`(8位純數字)不一樣——那份Excel只是文件說明,不代表正式匯出的CSV實際格式。**教訓:欄位格式不能只看資料字典,一定要對實際資料跑diagnose再寫解析邏輯。** 已修正regex與 `pd.to_datetime` 的format為 `%Y-%m-%d`。

**問題二:「NBU_CARD有49萬筆重複」是誤判,不是真的資料問題。** pandas的 `.duplicated()` 預設會把多個缺失值(NaN)互相視為「相等」,因此判定為重複。而NBU_CARD本身就有8.1%(約49萬筆)是缺失值,這些缺失值彼此被誤判成「重複」,數字換算後(49萬缺失-1 ≈ 49萬「重複」)剛好對得上原本的警告數字,證實不是真的同一張卡被登記兩次。已修正:重複值檢查前先 `dropna()`,排除缺失值再檢查。**教訓:檢查唯一性/重複值之前,一定要先排除缺失值,否則NaN會互相污染判斷結果。**

**驗證結果(修正後正式執行)**:`member_clean.csv` 產出成功,600萬筆會員紀錄,最終各欄位缺失比例:

| 欄位 | 缺失比例 |
|---|---|
| NBU_CARD | 8.1% |
| Age | 0.1% |
| Sex | 0.1%(另有6,503筆代碼不合理已轉缺失) |
| ZipCode5 | 2.8% |
| StoreId | 0.0% |
| TenureDays | 0.0% |

`NBU_CARD` 排除缺失值後確認沒有重複,可以放心當join key使用。`member_clean.csv` 產出完成,清洗階段到此結束。
